# Phase 4.5 Egress Hot-Path Closure Baseline

日期：2026-11-25

## 结论

Phase 4.5 完成了 QoS 0 Fanout 流水化、低优先级 Egress 调度、
`TryEnqueue` 无分配快路径和拓扑 A/B 工具，但 12 单元格开发门禁仍有
4 个红格，严格 MQTTnet 门禁 12/12 未通过。

因此 **Phase 5 保持阻塞**。不能把 Phase 4.5 标记为性能目标完成。

## 环境

- Windows 11 `10.0.26300`
- Intel Core i7-8565U，4 物理核 / 8 逻辑核
- .NET SDK `10.0.402`
- .NET Runtime `10.0.15`，X64 RyuJIT x86-64-v3
- Server GC、Concurrent GC、TieredPGO：启用
- ThreadPool 最小 Worker：8
- 默认拓扑：Event Loop Shards `8`，Kestrel IOQueue `8`
- MQTTnet `5.2.0.1603`

## 诊断证据

优化前 QoS 0/100/8 KiB Outbound 诊断：

- 发布数：1392
- 投递数：139200
- Egress Drain：137611
- 平均 Fanout：2522.1 us
- Flush Wait：784
- 最大 Pending 深度：17

这说明每次发布平均等待约 2.5 ms，且 Egress 几乎一条消息执行一次 Drain；
Flush 等待不是主要瓶颈。

优化后：

- QoS 0 发布方在所有目标 Shard Batch 入队后即可继续，不再等待远端投递完成。
- Egress Work 进入低优先级队列，在 Fanout Batch 高优先级队列让出后被调度。
- `TryEnqueue` 在队列有空位时同步入队，满队列才进入异步背压。
- 规划 Buffer 使用独占池，远端 Batch 全部完成或失败后归还。
- 目标 Shard FIFO 顺序通过三项连续 QoS 0 发布测试验证。

不能通过固定更少 Shard 解决。

## 未解除的风险

- QoS 0/100/8 KiB 的端到端吞吐和 p99 仍显著落后。
- 64 KiB QoS 0 单订阅者 p99 仍约 `9.4x` MQTTnet。
- Egress 平均批次提升有限；低优先级队列和一次让出改善吞吐，但两次/四次
  让出实验均导致退化，已回退。
- 当前证据仍指向接收端 Egress/网络发送吞吐和线程调度，而不是 Route
  Planner。

## 下一步

Phase 5 暂不开始。后续需要做架构级选择：

- 专用 Socket 发送队列与原 Kestrel PipeWriter A/B；
- 每连接跨发布的有界合批，而不是单次 Epoch 内的 Fanout 合批；
- 或调整默认拓扑策略，但必须同时证明 QoS 1 和单连接路径不退化。

在这些实验完成前，Phase 4.5 保持红色状态。
