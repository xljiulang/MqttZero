# Broker 1000 x 64 KiB Fanout Investigation

## Environment

- Windows 11, 12th Gen Intel Core i5-12450H
- .NET SDK 10.0.400, Release
- MQTTnet 5.2.0.1603
- QoS 1, 1,000 subscribers, 64 KiB payload
- One publisher, closed-loop delivery window of 1,024 messages

Command:

```powershell
dotnet run -c Release --no-build --project benchmarks/MqttZero.BrokerBenchmarks -- `
  compare --qos 1 --subscribers 1000 --payload 65536 `
  --warmup 3 --seconds 20 --repetitions 3 `
  --max-pending 1024
```

## Root Cause Of The Reported 0.53x Result

The previous comparison applied `--max-pending` only to QoS 0 and did not drain
the warmup before resetting counters. For QoS 1/2, publisher acknowledgement is
decoupled from subscriber delivery, so the warmup accumulated a large delivery
backlog that was then consumed inside the measurement window.

One diagnostic run demonstrated the contamination directly:

| Broker | Warmup published | Warmup received at cutoff | Reported ratio |
|---|---:|---:|---:|
| MQTTZero | 16,000 | 9,147 | 0.746x |
| MQTTnet | 5,000 | 4,595 | baseline |

The benchmark now applies the same closed-loop limit to every QoS and waits for
all warmup messages to reach subscribers before measurement starts.

## Corrected Result

Three 20-second repetitions, median values:

| Metric | MQTTZero | MQTTnet | Ratio |
|---|---:|---:|---:|
| Throughput | 1.9755 msg/s | 1.9596 msg/s | 1.008x |
| p99 publisher acknowledgement | 828,674 us | 624,633 us | 1.327x |

The 0.53x throughput collapse is not reproducible under the corrected
methodology. The throughput gate of at least `1.00x` is met, but the overall
cell gate remains red because p99 exceeds MQTTnet.

## Stage Evidence

Temporary instrumentation measured the subscriber batch path:

- Flush wait: more than 99% of accumulated send-path wall time.
- Encoding: approximately 0.5% of accumulated send-path wall time.
- Broker API enqueue: median approximately 4-6 ms for 1,000 sessions.

The dominant cost is therefore delivering roughly 64 MiB per published message
through 1,000 loopback TCP connections and processing it in 1,000 MQTTnet client
instances, not Broker encoding or queue insertion.

## Experiments Rejected

- Forcing Header and 64 KiB Payload into one contiguous PipeWriter span:
  throughput collapsed, approximately 0.07x-0.28x in single runs.
- `--fragmentation false` with a full intermediate packet buffer:
  throughput dropped to approximately 0.17x.
- Kestrel 1 MiB `MaxWriteBufferSize`: no material improvement.
- 1 MiB accepted-socket send buffer: no material improvement.
- `UnsafePreferInlineScheduling`: no material improvement.
- Inline `MqttZeroAsyncSignal` continuations: no material improvement.
- A high-limit global outbound concurrency semaphore: no improvement.
- Deferring all 1,000 pump signals until routing completes: worsened p99.
- Four-message large-packet batches: no material improvement for this workload.

## Retained Changes

- Closed-loop backpressure for QoS 0/1/2.
- Warmup drain before measurement.
- Warmup published/received counters in benchmark JSON.
- Multi-subscriber and stage-timing support in `outbound` mode.
- Single-segment fast path in PUBLISH property/payload writers.
- PUBLISH body length now reuses the already-computed property length.

The overall performance gate remains red because p99 is worse than MQTTnet.
This result must not be used as a capacity claim and the performance branch
must not be merged or released based on it alone.
