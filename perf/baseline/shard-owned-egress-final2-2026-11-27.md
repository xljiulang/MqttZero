# Shard-Owned Egress 第二轮最终判定（2026-11-27）

## 结论

- 三个关键格全部通过：QoS 1 / 100 / 64 KiB（主目标）**+1.5% / p99 0.835**、
  QoS 2 / 100 / 8 KiB **+3.4% / p99 0.885**、QoS 0 / 100 / 32 B **0.0% / p99 1.000**。
- QoS 0 / 100 / 8 KiB **+9.0% / p99 0.888**，同样通过。
- QoS 1 / 1 / 64 KiB 仍未过 p99（1.32），但该格的交付 p99 是 3.5–4.7 s，
  由订阅端吞吐与 64 条 64 KiB 的在途积压决定，不是 Broker 服务时间；吞吐（publish-window）
  +10.8% 说明 Broker 侧没有回退。
- 测量口径已落地：`DrainRatio > 0.10` 自动改用 publish-window 判定，报告记录
  `ThroughputMetric`；QoS 0 单订阅改用绝对 p99 预算（≤ 2000 µs）后从「不可判」变为可判。

## 方法与口径

`master@ec8ba3f` 对 `refactor/shard-owned-egress-timers@6820982`，同机交替、3 轮、
5 s 预热 / 20 s 测量、MQTTnet 客户端、单发布者、`--max-pending 1024`（延迟档为 64）。
诊断开关关闭，计数器零成本。

## 判定说明

QoS 1 / 1 / 64 KiB 的 p99 是「订阅端能否跟上」的度量：`--max-pending 64` 仍允许约 4 MB
在途，64 KiB × 500 msg/s 需要 32 MB/s 的单连接吞吐，客户端做不到，于是排空尾巴主导。
该格若要作为 Broker 延迟门禁，需要把在途再压到 8 条左右，或只对发布侧 p99 判定；
本轮不做，避免再一次用口径掩盖结论。

QoS 0 / 100 / 32 KiB 原本不在计划矩阵内（计划是 32 B），只作为额外观测记录，
不参与合并判定。
