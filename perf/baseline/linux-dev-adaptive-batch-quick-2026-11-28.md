# Linux 开发服务器自适应大包批次快速结果

## 结果

生产路径已对 `>= 32 KiB` 消息应用内部 `128 KiB / 2 条` 批次上限。由于
64 KiB PUBLISH 编码后超过 64 KiB，实际通常每条消息 Flush 一次。

三次 `-Quick` 结果：

| Run | MQTTZero delivery/s | MQTTnet delivery/s | 吞吐比 | 零/网 RSS MB | 累计分配 MB | Gen2 | 零/网 p99 ms |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 4189.8 | 4668.4 | 0.897 | 178.4 / 183.0 | 689.2 | 23 | 10447 / 10090 |
| 2 | 3898.4 | 4214.1 | 0.925 | 189.9 / 182.6 | 971.5 | 31 | 11244 / 10283 |
| 3 | 4306.7 | 4238.7 | 1.016 | 184.6 / 184.2 | 1125.5 | 37 | 10336 / 10120 |

中位数：

| 指标 | MQTTZero | MQTTnet | 比值 |
|---|---:|---:|---:|
| 吞吐 | 4189.8 delivery/s | 4238.7 delivery/s | 0.988x |
| p99 | 10447 ms | 10120 ms | 1.032x |
| 峰值 RSS | 184.6 MB | 183.0 MB | 1.008x |

## 判断

- 相比修复前约 `488 MB` RSS，内存已下降约 62%，并与 MQTTnet 基本持平。
- 累计分配中位数约 `972 MB`，低于快速门禁 `1 GB`。
- 吞吐中位数 `0.988x`，满足快速开发线 `0.98x`，但未达到最终 `1.00x`。
- p99 仍落后约 3.2%，后续需要继续优化，但不能通过放大批次重新引入内存问题。
- `MEMORYPROBE` 自身会触发额外对象和 GC，因此 Gen2 只记录，不作为快速硬门禁。

## 有效性

- 三次均为快速单轮，不是最终三轮中位数。
- 环境已停止 `intercom` Docker Compose 项目。
- 相同主机、相同提交、相同参数，MQTTZero/MQTTnet 交替运行。
- 最终结论仍要求完整三轮目标格测试。
